      #9.1. rokc CLI 인터페이스

      이 절에서는 컴파일러 rokc 의 명령줄 인터페이스를 정의합니다. toolchain 은 세 바이너리로 이루어집니다.

      바이너리역할
      rokc컴파일러 (rustc 에 해당). 빌드, 실행, 테스트, 포매터, 린터, REPL, LSP 를 담음 (이 절)
      rokcargo 식 front-end. 매니페스트, 의존성, 환경, toolchain 고정을 맡고 rokc 를 부름 (9.10)
      rokls편집기용 LSP 서버 실행 파일. rok lsp 와 같음

      런타임은 librokr.a (rokr) 입니다. 별도 도구 (rok-fmt 등) 는 두지 않습니다. rokc 는 의존성을 해소하지 않으며, 의존 패키지는 rok 가 --extern 으로 넘깁니다 (9.2.3).

      #9.1.1. 일반 형태

      rokc 는 다음과 같은 일반 형태로 호출됩니다.

      rokc <subcommand> [options] [args]

      문법 규칙으로 정리하면 아래와 같습니다.

      cli_invocation  ::= "rokc" subcommand option* arg*
subcommand      ::= "build" | "emit" | "run" | "test" | "bench" | "check"
                  | "fmt" | "lint" | "doc" | "repl" | "jupyter" | "lsp"
                  | "clean" | "profdata" | "bindgen" | "demangle" | "rokhir-text" | "inspect" | "version" | "help"
option          ::= "--" identifier ("=" value)?
                  | "-" letter

      --name value 는 --name=value 와 같습니다. 전역 옵션 (9.1.5) 은 서브명령 앞뒤 어디에나 둘 수 있습니다.

      영역서브명령
      빌드 / 실행build, emit, run, test, bench, check
      패키지clean
      도구fmt, lint, doc, lsp, profdata, bindgen
      인터랙티브repl, jupyter
      디버그 / 진단demangle, rokhir-text, inspect
      그 밖version, help

      #패키지 지정 (path)

      build / run / test / check / clean 의 [path] 는 다음 가운데 하나입니다. 생략하면 현재 디렉토리입니다.

      path패키지
      패키지 디렉토리그 디렉토리. src/main.rok 나 src/lib.rok 가 없으면 위로 찾음 (9.2.2)
      패키지 src/ 안의 파일그 패키지: 파일에서 위로 올라가며 처음 src/main.rok / src/lib.rok 가 있는 디렉토리
      그 밖의 파일그 파일 하나로 된 익명 실행 패키지 (4.16.8). 패키지 디렉토리 안이지만 src/ 밖에 있는 .rok 파일도 포함

      디렉토리를 주었는데 위로 올라가도 패키지가 없으면 에러입니다. 익명 패키지의 파일 서브모듈 (mod foo;) 은 그 파일 옆에 있습니다 (4.16.8).

      패키지 이름 (산출물 이름) 은 패키지 디렉토리의 이름이며, 익명 패키지는 파일 이름에서 .rok 를 뗀 것입니다.

      #9.1.2. 핵심 서브명령

      #rokc build: AOT 빌드

      rokc build 는 패키지를 AOT 로 빌드하는 서브명령입니다.

      rokc build [path]

      [path] 는 위의 패키지 지정 규칙을 따릅니다. 산출물은 9.2.15 의 profile 별 target/ 에 놓입니다. src/main.rok 는 target/<profile>/<name> 을, src/lib.rok 는 target/<profile>/lib<name>.a 와 인터페이스 target/<profile>/<name>.rokhir (9.4) 를 만들며, 둘 다 있는 패키지는 둘 다 만듭니다. profile 은 -O2 / -O3 / -Os (--release 포함) 이면 release, 그 밖에는 debug 이며, --target=<target> 이면 target/<name>/<profile>/ 입니다. --target-dir=<dir> 나 ROKC_TARGET_DIR 이 있으면 target/ 대신 그 디렉토리를 씁니다.

      옵션은 다음과 같습니다.

      • --release 는 최적화 빌드 (-O2 와 같음) 를 release profile 로 수행하며, 기본값은 debug profile 의 디버그 빌드 (-O0) 입니다. 두 profile 의 차이는 9.2.15 가 설명합니다.
      • --target-dir=<dir> 는 target/ 의 위치를 바꿉니다 (ROKC_TARGET_DIR 과 같음).
      • --extern <name>=<dir | src/lib.rok | <name>.rokhir | lib<name>.a> 는 의존 패키지 하나를 최상위 경로 name 에 mount 합니다 (9.2.3). 소스 (dir / src/lib.rok) 는 같은 빌드에서 함께 컴파일하고, 미리 빌드한 패키지 (.rokhir / .a, 하나를 주면 옆의 짝을 찾음) 는 ROKHIR 을 읽고 archive 를 링크합니다. 여러 번 쓸 수 있고, 보통 rok 가 채웁니다. name 은 식별자이며, 패키지 이름의 - 를 _ 로 바꾼 것입니다 (9.10.3). rok 은 표준 라이브러리용으로 예약되어 있습니다: --extern rok=.. 은 사용법 에러이며, rok 이라는 라이브러리 패키지는 거부합니다. 키워드와 경로 시작점 (pkg, sup) 도 name 으로, 또 라이브러리나 라이브러리가 있는 패키지의 이름으로 쓸 수 없습니다 (9.10.3).
      • --extern-feature <name>=<f> 는 소스 의존 패키지 name 을 cfg(feature = "<f>") 로 빌드합니다. feature 마다 하나씩, 여러 번 줄 수 있습니다. 의존 패키지가 보는 것은 이것뿐입니다: --cfg 의 feature 키는 컴파일 중인 패키지의 것입니다. 보통 rok 이 채웁니다.
      • --name <n> 은 패키지 이름 (9.10.3 의 이름 규칙) 을 정합니다. 산출물은 lib<n>.a / <n>.rokhir 이고 mount 이름은 - 를 _ 로 바꾼 것입니다. 기본은 디렉토리 이름입니다. --extern a-b=.. 도 a_b 로 묶습니다.
      • --bootstrap <file> 은 미리 읽을 표준 라이브러리 루트 (여러 번 가능), --rokr <lib> 는 링크할 런타임입니다. 기본값은 sysroot 의 lib/rok/{core,std,bare}/src/lib.rok 와 lib/librokr.a 입니다 (9.2.19). bootstrap 루트의 tier 는 그 src/ 위 디렉토리의 이름이며, bare 루트 없이 core/src/lib.rok 를 주면 그 옆의 bare/src/lib.rok 도 읽습니다. 찾지 못하면 찾아본 경로를 나열하는 에러입니다.
      • -O0 / -O1 / -O2 / -O3 / -Os 는 최적화 단계를 명시적으로 지정합니다. -O0 은 native backend 를, 나머지는 MLIR → LLVM backend 를 씁니다 (9.2.10).
      • --target=<target> 은 타깃 플랫폼을 지정합니다: 플랫폼 타깃 의 15 개 Tier 1 같은 내장 이름, 또는 <name>.rokon 타깃 명세 파일 (0.6.5). 어느 host 에서나 어느 대상이든 빌드할 수 있습니다 (0.2.4).
      • -L <dir> 은 #[link] 의 라이브러리 검색 디렉토리를 더합니다 (5.9.9). LIBRARY_PATH 보다 먼저 찾습니다. 여러 번 쓸 수 있습니다.
      • -l [static=|dylib=]<name> 은 라이브러리 <name> 을 링크하며 (#[link] 처럼 찾음), --native-runtime <file> 은 실행 파일 옆에 둘 공유 라이브러리를 지정합니다 (9.2.14). 둘 다 여러 번 쓸 수 있으며, rok 가 native 패키지에 대해 넘깁니다 (9.10.4b).
      • -o / --out=<path> 는 출력 위치를 지정합니다.
      • --cfg <flag> / --cfg <key>=<value> 는 조건부 컴파일 의 cfg flag 를 설정합니다. 여러 번 쓸 수 있습니다.
      • --emit=<kind>[,<kind>..] 는 중간 산출물 (ast, hir, mir, mlir, llvmir, asm, obj, expanded) 을 target/<profile>/build/<name>.<ext> 에 씁니다 (9.9.1). 쉼표로 여러 종류를 한 번에 지정하며, 이때는 -o 를 함께 쓸 수 없습니다. --emit 이 있으면 실행 파일이나 archive 는 만들지 않습니다.
      • --load-mlir-plugin <path|name> 은 MLIR 다이얼렉트 plugin 을, --load-mlir-pass-plugin <path|name> 은 패스 plugin 을 (둘 다 rokc 의 MLIR 에, 같은 고정 LLVM 으로 빌드하고 Windows 에서는 rokc.exe 의 import library 에 링크한 것을) 로드하고, --mlir-pass <pass> 는 LLVM 다이얼렉트로 변환하기 전에 그 패스를 실행합니다 (rok::bare::mlir::plugin). 모두 여러 번 쓸 수 있으며, rok 도 그대로 넘깁니다.
      • -g 는 release profile 빌드에 디버그 정보를 더합니다: DWARF, Windows 대상에서는 PDB 의 CodeView (9.9.6). debug profile 빌드에는 항상 있습니다.
      • -C overflow-checks[=yes|no] 는 고정 폭 정수 산술의 overflow 검사 (panic) 를 켜거나 끕니다. 기본값은 -O0 에서만 켬입니다. 값을 생략하면 yes 입니다. overflow 가 일어날 수 없는 상수 피연산자 연산은 검사를 생략합니다.
      • -C backend=native|llvm 은 최적화 수준이 고른 backend 를 바꿉니다 (9.2.10).
      • -C target-cpu=<cpu>|native 는 triple 의 baseline 대신 그 CPU 를 대상으로 합니다 (0.6.4). native 는 빌드하는 기계의 CPU 입니다. -C target-feature=+f1,-f2,.. 는 개별 기능 (+avx2 등) 을 켜거나 끕니다. 그렇게 만든 바이너리는 그 기능이 없는 CPU 에서 돌지 않을 수 있습니다. native backend (-O0) 에서는 이 옵션을 경고로 알리고 baseline 용으로 빌드합니다. native 는 target 이 host 플랫폼일 때만 받습니다.
      • -C subsystem=console|windows 는 Windows subsystem 을 고릅니다: console (기본, mainCRTStartup) 또는 windows (GUI, WinMainCRTStartup, 9.5.9).
      • -C profile-generate[=<dir>] 는 profile-guided optimization 을 위해 프로그램과 소스 의존 패키지를 계측합니다. 실행하면 raw profile <dir>/default_%m.profraw 를 씁니다 (기본 <dir>: 실행 시점의 작업 디렉토리, LLVM_PROFILE_FILE 이 경로를 바꿈). 계측된 실행 파일은 toolchain 이 대상용으로 제공하는 profile 런타임을 링크합니다 (9.2.19). wasm32-unknown-unknown 에서는 지원하지 않습니다 (파일 시스템 없음).
      • -C cs-profile-generate[=<dir>] 은 -C profile-use 와 함께 inlining 뒤에 다시 계측합니다 (context-sensitive). 그 실행들을 그 profile 과 합치면 -C profile-use 가 읽는 profile 하나가 됩니다.
      • -C profile-use=<file> 은 rokc profdata merge 로 만든 indexed profile 로 최적화합니다. 파일이 없으면 에러입니다. profile 을 기록한 뒤 제어 흐름이 바뀐 함수는 그것 없이 최적화하며, 그 수를 경고 하나로 알립니다.
      • 둘 다 어느 수준에서나 MLIR → LLVM backend 를 고르며, 함께 쓰는 -C backend=native 는 에러입니다. 표준 라이브러리는 cache 에서 가져오지 않고 프로그램과 함께 컴파일되므로 함께 profile 되고 최적화됩니다. REPL 은 둘 다 거부합니다.

      rokc build 는 패키지의 lint 진단을 rokc check 처럼 보고합니다 (6.2.9): 경고는 출력하고 빌드를 이어 가며, deny lint 는 빌드를 실패시킵니다. 이전 빌드 뒤로 바뀐 것이 없으면 rokc build / rokc run 은 Fresh 를 출력하고, 그 빌드의 경고를 다시 출력하며, 빌드를 건너뜁니다 (9.2.16).

      #rokc profdata merge: profile 병합

      rokc profdata merge [-o <file>] <file | dir>...

      raw (.profraw), indexed (.profdata), text (.proftext, LLVM 의 text profile 형식) profile 을 -C profile-use 용 indexed profile 하나 (기본 default.profdata) 로 합칩니다. 디렉토리는 그 안의 그런 파일들을 뜻하며, 빈 raw profile 은 건너뜁니다. 프로세스 안에서 실행합니다. 병합 경고 (counter overflow, counter 불일치) 는 보고하며, 병합은 그래도 결과를 씁니다.

      #rokc profdata show: profile 요약

      rokc profdata show [--all-functions] [--topn N] <file>

      profile 의 요약을 llvm-profdata show 형태로 출력합니다: 계측 수준과 보인 함수 수, 전체 함수 수. --all-functions 는 함수마다 hash 와 counter 를 더하고, --topn N 은 내부 block count 가 가장 큰 N 개 함수를 나열합니다.

      #rokc emit: 중간 산출물

      rokc emit [path] [--emit=<kind>[,<kind>..]]

      rokc build --emit=.. 와 같습니다. --emit 을 생략하면 mlir 입니다.

      #rokc run: 빌드 후 실행

      rokc run 은 빌드 직후 산출물을 바로 실행하는 명령입니다.

      rokc run [path] [-- args...]

      실행 패키지를 빌드한 뒤 곧바로 실행하며, -- 뒤에 적은 인자는 실행 파일에 그대로 전달됩니다. 옵션은 rokc build 와 동일합니다. 라이브러리 패키지에는 실행할 것이 없으므로 에러입니다.

      패키지는 target/<profile>/<name> 에 빌드하고, 익명 패키지 (단일 파일) 는 임시 디렉토리에 빌드하므로 파일 옆에 target/ 을 만들지 않습니다. rokc build <file>.rok 은 익명 패키지도 target/ 에 빌드합니다.

      rokc run hello.rok -- arg1 arg2

      rokc run 의 종료 코드는 프로그램의 종료 코드입니다. 프로그램이 시그널 n 으로 끝나면 128 + n 입니다.

      #rokc test: 테스트

      rokc test 는 테스트 함수들을 모아 테스트 하네스를 빌드하는 명령이며, 실행은 rok test (9.10) 가 합니다.

      rokc test [path] [filter]

      #[test] 가 붙은 함수를 모아 테스트 실행 파일 (하네스) 을 빌드합니다. #[test] 는 #[cfg(test)] 를 함의하므로 (6.2.5) 테스트 함수는 일반 빌드에 들어가지 않습니다. 테스트는 src/ (#[cfg(test)] 아래) 와 tests/ 디렉토리 (0.3.5) 양쪽에서 모읍니다. 테스트 빌드에서는 패키지의 진입점 대신 테스트를 고르는 진입점이 쓰입니다.

      rokc 는 하네스를 실행하지 않습니다. --emit-harness <file> 는 빌드된 실행 파일과 그 안의 테스트 - rok test 가 실행하는 매니페스트 - 를 <file> 에 씁니다. 주지 않으면 빌드된 실행 파일을 표준 에러에 알립니다. 하네스 실행 (테스트 선택, 아래의 프로세스 격리·병렬·보고) 은 rok test 러너 (9.10) 가 맡습니다.

      인자가 하나이고 존재하는 경로가 아니면 그것을 filter 로 봅니다. filter 는 모듈 경로를 포함한 테스트 이름 (math::adds) 에 맞춥니다.

      • ^ $ . * + ? 와 \ 이스케이프를 쓰는 작은 정규식입니다. 고정하지 않은 검색이므로 ^ / $ 가 없으면 이름의 어느 부분과 맞아도 됩니다.
      • 이 문자들이 없으면 단순 부분 문자열 검색과 같습니다.

      각 테스트는 자기 프로세스에서 실행됩니다. 테스트가 panic 하거나 (종료 코드 101) 잡히지 않은 에러로 끝나면 (종료 코드 1) 그 테스트만 실패하고 나머지는 계속 실행됩니다. 시그널로 끝나도 실패입니다.

      옵션은 rokc build 와 동일하며, 추가로 다음 두 가지를 지원합니다.

      • --threads=N 은 동시에 실행할 테스트 프로세스 수를 지정합니다. 기본값은 ROKC_NUM_JOBS, 그것도 없으면 CPU 수입니다.
      • --show-output 은 성공한 테스트의 stdout / stderr 까지도 표시합니다. 실패한 테스트의 출력은 늘 표시합니다.

      출력은 stdout 에 다음 형태로 나옵니다.

      running 3 tests
test math::adds ... ok
test math::subs ... FAILED
test util::trims ... ok

failures:

---- math::subs ----
<그 테스트의 stdout / stderr>
(panicked (exit 101))

failures:
    math::subs

test result: FAILED. 2 passed; 1 failed; 0 filtered out; finished in 0.12s

      실패한 테스트가 하나라도 있으면 종료 코드는 1 입니다.

      루트 파일이 둘 다 있는 패키지에서는 라이브러리의 테스트를 먼저, 그다음 실행 파일의 테스트를 (테스트 없는 라이브러리에 대해 빌드해) 실행합니다. 라이브러리 실행이 실패하면 명령이 끝납니다. run 과 bench 도 같은 방식입니다.

      #rokc bench: 벤치마크

      rokc bench [path] [filter]

      #[bench] 가 붙은 함수를 모아 최적화 빌드 (-O 를 주지 않으면 -O2) 로 빌드하며, rok bench (9.10) 가 하네스를 실행해 측정합니다 (9.9.11). #[bench] 는 #[test] 처럼 #[cfg(test)] 를 함의하며, 벤치는 src/ 와 benches/ 디렉토리 (0.3.5) 양쪽에서 모읍니다. path, filter, --emit-harness 규칙은 rokc test 와 같습니다.

      벤치마크는 Bench 핸들을 받아 클로저를 측정하므로, setup 은 측정 밖에 둡니다:

      #[bench]
fn parse_1kb(b: Bench) {
    let input = sample(1024);               // setup: 한 번만, 측정 안 함
    b.bytes(1024);                          // 선택: 처리량 보고
    b.iter(|| parse(black_box(input)));     // 측정 구간
}

      b.iter(f) 가 측정 전체 (보정, warm-up, 표본)를 수행하며, 결과는 black_box 처리됩니다. black_box (rok::core) 는 옵티마이저가 꿰뚫어 볼 수 없는 항등 함수로 - 측정 구간의 입력과 결과에 적용해 작업이 밖으로 끌려 나가거나 접히지 않게 합니다. b.bytes(n) / b.items(n) 은 처리량 열을 더합니다. Bench, black_box, 통계는 라이브러리 API 이고, 방법론은 9.9.11 에 정의합니다.

      • --iters=N 은 보정 대신 표본 하나의 호출 횟수를 고정합니다.
      • --samples=N 은 측정할 표본 수입니다 (기본 100).

      벤치는 하나씩 차례로 실행됩니다. 터미널 출력은 벤치마다 한 줄, 사람이 읽는 단위로 정렬되고, stdout 이 터미널이 아니면 회귀 도구를 위한 안정적인 기계 가독 형식이 쓰입니다.

        json::parse_1kb     1.84 us +/- 0.03 us   543 MiB/s   [2 outliers]

      #rokc repl: 터미널 REPL

      rokc repl 은 터미널에서 인터랙티브 셸을 띄워 주는 명령입니다.

      rokc repl [path]

      이 모드는 터미널 인터랙티브 셸로 동작합니다. 셀의 의미는 9.7.0 의 규칙을 따릅니다. 각 셀은 한 번만 실행되고, top-level let 바인딩과 항목은 이후 셀로 이어지며, 실패한 셀은 바인딩에 흔적을 남기지 않습니다. 식 셀은 타입: 값 을 출력합니다.

      • 기본 모드는 각 셀을 native backend 로 컴파일해 세션 동안 사는 JIT host 프로세스에 넘기고, host 가 그것을 로드해 한 번 실행합니다 (9.6). 바인딩, static 상태, any 값이 셀 사이에 이어집니다. 최상위에서 이름을 적을 수 없는 타입 (클로저, 비공개 타입 등) 의 바인딩은 만들 때 거부합니다.
      • 진단과 panic 위치는 셀 자신의 텍스트 기준 <repl>:line:col 로 표시합니다.
      • 입력은 줄 편집과 history 를 지원하며, history 는 $ROK_HOME/repl_history 에 남습니다.
      • 경로가 없으면 빈 세션으로 시작합니다. 프로그램 경로 (단독 .rok 파일이나 src/main.rok 가 있는 패키지) 는 로드해 실행하며 (top-level 문은 셀로, fn main 은 진입점으로), 세션이 이어집니다 (9.7.10). 라이브러리 패키지 경로 (src/lib.rok) 는 의존성으로 붙이고 use <name>::*; 를 첫 셀로 넣으며, :reset 뒤에도 다시 넣습니다.
      • 경로가 둘 이상이면 사용법 에러입니다. - 는 받지 않으며, 표준 입력은 셀 입력입니다.

      루트 파일이 둘 다 있는 패키지는 프로그램 경로이며, 그 라이브러리는 세션의 의존 패키지입니다. rok 와 rok repl (9.10) 은 의존성을 붙여 같은 REPL 을 실행합니다.

      REPL 명령 (:type, :reset, :add, :help, :quit) 과 디버그 수단은 9.9.9 에 있습니다.

      #rokc jupyter: Jupyter 커널

      rokc jupyter 는 Jupyter 가 호출하는 커널 모드를 제공합니다.

      rokc jupyter [--connection-file <path>]

      이 명령은 Jupyter 가 호출하는 커널 모드이므로 사용자가 직접 실행하지는 않습니다. --connection-file 은 Jupyter 가 제공하는 ZMQ 연결 정보 파일의 경로를 받으며, --extern 같은 빌드 옵션도 함께 받습니다. 커널은 REPL 과 같은 셀 세션 (9.7.0) 위에서 동작합니다. 의존성을 해소해 실행하려면 rok jupyter --connection-file <path> (9.10) 를 씁니다. 자세한 통합 내용은 Jupyter 통합 에서 정의합니다.

      커널 등록은 rok jupyter install [--env <name>] 이 합니다 (9.8.3).

      #rokc fmt: 포매터

      rokc fmt 는 표준 포맷을 적용하는 포매터 명령입니다.

      rokc fmt [path]

      [path] 는 파일 또는 디렉토리를 받으며 (여러 개 가능, 생략하면 현재 디렉토리), 표준 포맷 에 맞게 in-place 로 수정합니다. 패키지인 디렉토리 (9.2.2) 는 그 src/ 와 tests/ 디렉토리, 그리고 rok.rokon 을 포맷하며, 그 안의 다른 파일은 건드리지 않습니다. 디렉토리는 재귀로 .rok 파일을 찾으며 target/ 과 . 으로 시작하는 디렉토리는 건너뜁니다. .rokon 파일 (ROKON) 은 ROKON 인지 검사하고 들여쓰기만 다시 맞춥니다 (정규 형식으로 다시 쓰지 않으므로 주석이 남음).

      옵션은 다음과 같습니다.

      • --check 는 파일을 바꾸지 않고, 바뀔 파일과 그 diff 를 출력합니다. 바뀔 파일이 있으면 종료 코드 1 이며, CI 용도로 적합합니다.
      • --diff 는 파일을 바꾸지 않고 diff 만 출력합니다.

      어휘 에러가 있는 파일은 건드리지 않고 에러를 보고하며, 종료 코드는 1 입니다.

      #rokc check: 진단

      rokc check [path] [--check-library]

      front end 를 타입 검사와 MIR 생성까지 돌리고 lint 와 함께 진단을 냅니다. 코드 생성 (MLIR 포함) 은 하지 않습니다. 옵션은 rokc build 와 같습니다. --check-library 는 도달 여부와 무관하게 라이브러리의 모든 본문을 낮추고 검사하며, 모든 제네릭 본체를 그 바운드에 맞춰 검사합니다 (2.10.9). 루트 파일이 둘 다 있는 패키지는 라이브러리를 검사하고, 라이브러리에 에러가 없으면 라이브러리를 함께 컴파일한 실행 파일을 검사합니다. 각 경고는 한 번만 보고합니다.

      #rokc lint: 린터

      rokc lint [path] [--list]

      rokc check 에서 코드 생성을 뺀 것입니다. 컴파일하는 모든 명령이 같은 lint 를 보고하며 (6.2.9), lint 는 그것과 front end 만 돌립니다. 진단 형식은 9.1.8, lint 진단의 코드는 E503 입니다. lint 목록과 그룹은 6.2.9 에 있습니다. --list 는 lint 와 그룹, 기본 수준을 출력합니다.

      lint 수준은 전역 옵션 -A / -W / -D (9.1.5) 와 코드의 속성이 정합니다. deny 수준의 lint 가 하나라도 걸리면 종료 코드는 1 입니다.

      #rokc doc: 문서 생성

      rokc doc [path] [--std]

      패키지의 라이브러리 (없으면 실행 파일) (와 --extern 의존 패키지) 의 공개 항목과 문서 (///, //!, #[doc], 6.2.8) 로 HTML API 문서를 target/doc/ 에 만듭니다.

      target/doc/
├── index.html                 # 패키지 목록
├── <pkg>/<mod>/index.html     # 모듈마다 한 쪽
└── search-index.js            # 검색용 색인

      --std 는 표준 라이브러리 tier 도 rok-core/, rok-std/, rok-bare/ 로 문서화합니다. 경로가 없으면 그것만 ./target/doc/ 에 만듭니다.

      문서 텍스트는 markdown 의 부분집합 (제목, fenced 코드 블록, 인라인 코드, 링크, **굵게**, 목록, 문단) 으로 해석합니다.

      #rokc lsp: LSP 서버

      rokc lsp 는 Language Server Protocol 서버 모드로 동작합니다.

      rokc lsp

      이 모드는 VS Code, Vim, Emacs 등 LSP 클라이언트에서 호출하도록 설계됩니다. 편집기용 독립 바이너리 rokls 는 rok lsp (곧 rokc lsp) 와 같습니다. .rokon 버퍼는 구문만 검사합니다. 루트 파일이 둘 다 있는 패키지에서는 라이브러리의 모듈 트리가 닿는 파일을 라이브러리의 일부로, 그 밖의 파일을 실행 파일의 일부로 검사하며, 실행 파일은 라이브러리의 열린 버퍼를 봅니다. 기능 목록은 9.9.13 에 있습니다.

      #9.1.3. 디버그 / 진단 서브명령

      #rokc bindgen: C 헤더 binding

      rokc bindgen <header> [--target <t>] [-o <file>] [-- <clang args>]

      <header> 에 대한 std 1.7.6 의 선언을 표준 출력 (또는 -o <file>) 에 씁니다. toolchain 의 libclang (9.2.19) 이 없으면 찾아본 곳을 알리는 에러 (exit 1) 입니다.

      #rokc demangle: 심볼 demangle

      rokc demangle 은 mangled 심볼을 사람이 읽을 수 있는 형식으로 풀어 출력합니다.

      rokc demangle <symbol>...

      심볼마다 9.5.4 형식의 블록을 빈 줄로 나눠 출력합니다 (9.9.3). rok 심볼이 아닌 인자가 있으면 종료 코드는 1 입니다.

      #rokc rokhir-text: ROKHIR 텍스트 출력

      rokc rokhir-text 는 미리 빌드한 라이브러리의 ROKHIR 을 텍스트로 출력합니다.

      rokc rokhir-text path/to/foo.rokhir      # 또는 libfoo.a - 옆의 foo.rokhir 를 읽음

      header 필드, producer, meta 와 interface 파일들을 출력하며, 포맷은 ROKHIR 포맷 에 기술됩니다.

      #rokc inspect: 패키지 검사

      rokc inspect 는 archive 의 내용을 한눈에 살펴볼 수 있도록 합니다.

      rokc inspect path/to/libfoo.a        # 또는 foo.rokhir

      패키지 이름과 해시, rokc 버전, ROKHIR 버전, GC type id 구간, exports, generic items, archive 멤버와 크기를 한 번에 표시합니다 (9.9.14).

      #9.1.4. 보조 서브명령

      #rokc clean: 빌드 산출물 제거

      rokc clean 은 빌드 산출물을 제거하는 명령입니다.

      rokc clean [path]

      패키지의 target/ 디렉토리 전체 (모든 profile 과 교차 빌드 포함, --target-dir / ROKC_TARGET_DIR 이 있으면 그 디렉토리) 를 삭제합니다. 없으면 아무 일도 하지 않습니다.

      #rokc version: 버전

      rokc version
rokc --version            # = -V
rokc -V -v                # host 줄 추가

      stdout 에 rokc <버전> (<commit> <date>) 한 줄을 출력합니다. -v 를 더하면 host: <triple> 과 llvm: <version> 줄을 덧붙입니다.

      #rokc --print cfg: 활성 cfg

      rokc --print cfg [--target=<target>] [-O<n>] [--cfg ..]

      옵션이 가리키는 빌드의 cfg (6.3) 를 한 줄에 하나씩 출력합니다: 플래그는 flag, 키는 key="value" (rustc 와 같음). 키에는 target_env 가 있고, debug_assertions 는 -O0 에서 켜집니다.

      debug_assertions
target_arch="aarch64"
target_endian="little"
target_family="unix"
target_os="macos"
target_pointer_width="64"

      #rokc --print target-list / target-spec: 타깃

      rokc --print target-list
rokc --print target-spec [--target=<target>]

      target-list 는 내장 타깃 이름을 한 줄에 하나씩 출력합니다. target-spec 은 타깃의 명세를 ROKON 으로 출력하며 (0.6.5), --target 이 없으면 host 의 것입니다.

      #rokc --print lldbinit: lldb formatter

      이 toolchain 의 lldb formatter (9.9.6) 를 로드하는 한 줄 command script import '<path>' 을 출력합니다: <sysroot>/lib/rok/lldb/rok_lldb.py.

      #rokc help: 도움말

      rokc help [subcommand]
rokc <subcommand> --help

      서브명령을 주면 그 명령의 도움말을 보여 줍니다.

      #9.1.5. 전역 옵션

      전역 옵션들은 다음 표와 같습니다. 서브명령 앞뒤 어디에나 둘 수 있습니다.

      옵션의미
      --verbose / -v단계별 시간 표시 (9.9.5)
      -vv더 자세한 로그: Reading <file> 과 Specialized <path>(sig) 줄 (9.9.5)
      --quiet / -q진행 줄을 출력하지 않음 (진단은 출력)
      --color=auto|always|never진단의 색상 출력
      --no-color--color=never 와 같음
      --cwd=<path>작업 디렉토리를 바꾼 뒤 실행
      --print cfg|target-list|target-spec|lldbinit활성 cfg, 내장 타깃 이름, 타깃 명세, 또는 rok 의 formatter 를 로드하는 lldb 명령을 출력 (9.1.4)
      --message-format=human|json진단 형식. json 은 stdout 에 한 줄씩 (9.1.8)
      -A / -W / -D <lint | group>lint 수준 (--allow / --warn / --deny). 패키지를 컴파일하는 모든 명령 (build, run, test, bench, emit, check, lint, lsp) 에 적용. 여러 번 쓸 수 있고 뒤의 것이 이김

      lint 수준은 lint 의 기본 수준 < -A / -W / -D < 코드의 #[allow(..)] / #[warn(..)] / #[deny(..)] (가장 안쪽이 이김) 순으로 정합니다. rok 는 매니페스트의 lints 를 이 플래그로 앞에 붙여 넘깁니다 (9.10.1).

      --color=auto (기본값) 는 stderr 가 터미널이고 환경 변수 NO_COLOR 가 없을 때 색을 씁니다.

      사용 예는 다음과 같습니다.

      rokc --verbose build
rokc test -q
rokc --cwd=examples/hello run

      #9.1.6. 종료 코드

      종료 코드는 다음과 같이 정의됩니다.

      코드의미
      0성공
      1사용자 코드 에러 (컴파일 에러 / 테스트 실패 등)
      2사용법 에러 (잘못된 옵션, 모르는 서브명령 등)
      101rokc 내부 에러 (panic)

      rokc 는 ROK_HOME 을 읽지 않습니다 (sysroot 는 실행 파일 기준). rokc 자신이 panic 하면 (internal compiler error) 메시지를 출력하고 101 로 끝납니다. rokc lsp, rokc repl, rokc jupyter 는 이것을 견딥니다: language server 는 분석한 버퍼의 에러 진단으로 보고하고, REPL / kernel 은 그 셀을 실패시킵니다 (9.7.5). 둘 다 계속 서비스합니다. rokc run 은 실행한 프로그램의 종료 코드로 끝납니다 (9.1.2).

      표준 출력이나 표준 에러가 읽는 쪽이 사라진 pipe 이면 rokc 는 메시지 없이 멈춥니다: Unix 에서는 SIGPIPE 로 종료되고 (shell 은 141 을 보고), Windows 에서는 1 로 끝납니다. 이것은 내부 에러가 아닙니다.

      #9.1.7. 환경 변수

      rokc 의 동작에 영향을 주는 환경 변수는 다음 표와 같습니다.

      변수의미
      ROK_CC내장 lld 대신 마지막 링크를 하는 선택적 C 컴파일러 드라이버 (9.2.14)
      ROK_BACKENDnative 또는 llvm. -C backend= 와 같음
      ROKC_VERBOSE--verbose 와 동일
      ROK_TIME_PASSES1 이면 패스별 실제 시간을 stderr 에 출력 (9.9.5)
      LLVM_PROFILE_FILE계측된 프로그램 (-C profile-generate) 이 읽음: raw profile 경로
      ROKC_TARGET_DIRtarget/ 의 위치 (기본은 패키지 안)
      ROKC_INCREMENTALfront end 가 패키지의 파싱과 lowering 한 본체를 두는 곳 (기본 target/<profile>/incremental/, 0: 두지 않음). 라이브러리의 모은 항목은 lib/rok-cache/library/ 에 둠 (9.2.16)
      ROKC_INCR_VERIFY1: 모든 본체를 다시 lowering 하고 다르면 실패 (9.2.16)
      ROKC_NUM_JOBSrokc test --threads 의 기본값 (없으면 CPU 코어 수)
      NO_COLOR있으면 --color=auto 가 색을 쓰지 않음

      설정하지 않았거나 비어 있는 변수는 기본값을 가집니다. 나열된 것 밖의 값은 변수, 값, 받는 값을 알리는 경고 한 줄을 stderr 에 출력하며, 그 변수는 기본값을 가집니다.

      #9.1.8. 출력 형식

      #진단 메시지

      진단 메시지는 다음과 같은 형식으로 출력됩니다.

      error[E100]: cannot find value `count` in this scope
  --> src/main.rok:5:13
   |
 2 |     let counter = 0;
   |         ------- similar name defined here
...
 5 |     let x = count + 1;
   |             ^^^^^ not found in this scope
   |
   = help: did you mean `counter`?

      소스 파일 에서 정의한 파일 + 줄 + 컬럼 단위의 진단을 그대로 사용합니다.

      머리줄은 <severity>[<code>]: <message> 이고 --> path:line:col 이 주 위치입니다. 주 span 은 ^, 보조 span 은 - 로 밑줄을 긋고, 다른 파일의 보조 span 은 ::: path:line:col 로 시작합니다. 끝의 = note: 줄은 맥락을, = help: 줄은 고치는 방법을 덧붙입니다.

      #빌드 진행

      진행 상황은 stderr 에 오른쪽 정렬한 동사로 표시됩니다. -q 면 출력하지 않습니다.

         Compiling foo (path/to/foo)
    Building target/debug/foo
    Finished in 1.23s
     Running `target/debug/foo`
      동사시점
      Compiling프론트엔드 시작 (패키지 이름과 디렉토리)
      Building실행 파일 / archive 생성 (build)
      Wrote--emit 산출물 하나를 씀
      Finished빌드 끝 (걸린 시간)
      Running프로그램 실행 (run)
      Created패키지 생성 (new)
      Removedtarget/ 삭제 (clean)

      #JSON 출력 (도구 통합용)

      도구 통합을 위해서는 JSON 형식으로도 출력할 수 있습니다.

      rokc build --message-format=json

      이 모드에서는 진단 하나가 stdout 의 한 줄 JSON 객체가 되므로, IDE 와 CI 도구에서 쉽게 파싱할 수 있습니다. 객체의 모양은 9.9.4 에서 정의합니다.

      #9.1.9. 표준 입력

      rokc check - 처럼 인자 자리에 - 를 적으면 표준 입력을 의미하며, 파이프 또는 스크립트 통합 용도로 활용할 수 있습니다. 표준 입력의 소스는 익명 실행 패키지의 main.rok 로 검사합니다.

      #9.1.10. 외부 도구와의 호환

      rokc 는 저수준 컴파일러이며, 의존성 해소는 front-end rok (9.10) 가 맡습니다. rok 는 해소한 의존 패키지의 루트를 --extern (9.2.3) 으로 넘겨 rokc 를 부릅니다. 다른 빌드 시스템도 같은 방식으로 rokc 를 직접 호출해 통합할 수 있습니다. CLI 호환성을 깨는 변경은 SemVer 규칙에 따라 관리됩니다.

      #9.1.11. 표준 포맷 (rokc fmt)

      rokc fmt 의 표준 포맷은 토큰을 보존하는 배치 규칙 입니다. 줄 안의 토큰과 주석은 바꾸지 않고 줄의 들여쓰기와 공백 줄만 정합니다. rokc fmt 는 의도적으로 설정이 없습니다: 모든 rok 코드에 표준 포맷은 하나입니다.

      1. 들여쓰기는 괄호 (( [ { #[) 깊이마다 공백 4 칸입니다. 닫는 괄호로 시작하는 줄은 여는 줄의 깊이를 따릅니다. 탭은 공백으로 바뀝니다.
      2. 이어지는 줄, 곧 앞 토큰이 ; , 나 괄호가 아닌 줄 (긴 식을 나눈 줄 등) 은 원래 파일에서 블록 들여쓰기보다 더 들여쓴 만큼을 유지합니다.
      3. 줄 끝 공백을 지웁니다.
      4. 연속된 빈 줄은 하나로 줄이고, 파일 처음의 빈 줄은 지웁니다.
      5. 파일은 줄바꿈 하나로 끝납니다.

      포매터는 토큰을 줄 사이로 옮기지 않고, 줄을 나누거나 합치지 않으며, 줄 안의 간격을 바꾸지 않습니다. 따라서 주석은 적힌 그대로 남고 토큰 열은 바뀌지 않습니다. 여러 줄에 걸친 문자열과 블록 주석의 안쪽도 그대로 둡니다.
