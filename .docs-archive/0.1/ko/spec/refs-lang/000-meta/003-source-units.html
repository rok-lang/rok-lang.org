      #0.3. 소스 단위

      rok 의 컴파일 단위는 패키지입니다. 패키지는 파일 시스템 위에서 정해진 규약 (src/main.rok / src/lib.rok) 으로 인식됩니다. 매니페스트 rok.rokon 은 의존성 등을 선언할 때만 두며, 의존성이 없는 패키지에는 필요하지 않습니다 (0.3.4).

      #0.3.1. 실행 파일과 라이브러리

      패키지는 실행 파일, 라이브러리, 또는 둘 다를 가집니다. 무엇을 가지는지는 소스 디렉토리 src/ 의 루트 파일만으로 정해집니다: src/main.rok 는 실행 파일의 루트, src/lib.rok 는 라이브러리의 루트입니다.

      패키지 디렉토리는 패키지의 소스를 src/ 에 두고, 그 밖의 모든 것을 그 옆에 둡니다: 매니페스트 rok.rokon 과 lockfile rok.lock (0.3.4), target/ (빌드 산출물, 9.2.15), 그리고 README, LICENSE, 테스트 데이터 같은 파일입니다. src/ 아래의 파일만 패키지의 소스이며, src/ 밖의 .rok 파일은 패키지의 일부가 아닙니다 (함께 컴파일되지 않고, 식별자 (0.3.3) 에 들어가지 않으며, 따로 실행하면 익명 패키지입니다, 4.16.8). 유일한 예외는 tests/ 와 benches/ 디렉토리로, rokc test / rokc bench 에서만 컴파일됩니다 (0.3.5).

      #실행 패키지: src/main.rok

      src/main.rok 가 있는 디렉토리는 실행 패키지로 인식됩니다.

      my_app/
├── rok.rokon         <- manifest (optional, 0.3.4)
├── src/
│   ├── main.rok      <- entry point
│   └── ...           <- other module files
└── target/           <- build output

      main.rok 는 진입 모듈로서, 명시적인 fn main 이나 top-level 문 가운데 한 가지 형태로 진입점을 제공합니다. 진입점의 정확한 형태와 top-level 문의 의미는 4.16 진입점 에서 정의합니다. 패키지에 속하지 않은 단일 파일을 실행하면 그 파일이 익명 패키지의 main.rok 로 취급됩니다 (4.16.8).

      #라이브러리 패키지: src/lib.rok

      src/lib.rok 가 있는 디렉토리는 라이브러리 패키지로 인식됩니다.

      my_lib/
├── rok.rokon
└── src/
    ├── lib.rok       <- library root
    └── ...

      라이브러리 패키지에는 진입점이 없으며, 외부에서 불러서 쓰는 정의 묶음의 역할을 합니다. lib.rok 를 포함한 main.rok 이외의 모든 모듈 파일은 항목만 담을 수 있고 top-level 문을 둘 수 없으므로, 모듈을 가져오는 일은 어떤 코드도 실행하지 않습니다 (4.16.6).

      #한 패키지의 라이브러리와 실행 파일

      패키지는 src/main.rok 와 src/lib.rok 를 둘 다 가질 수 있습니다. 그것들은 하나의 src/ 에서 빌드하는 두 target 입니다: 라이브러리와, 그것을 쓰는 실행 파일. 실행 파일은 라이브러리를 패키지 이름을 딴 의존 패키지로 봅니다 (use my_app::parse;; 9.10.3 의 코드 이름, - 를 _ 로 바꾼 것). 라이브러리는 실행 파일과 별개의 패키지입니다: 거기서는 pub 항목만 보이며 pub(pkg), pub(sub), 비공개 항목은 보이지 않고 (5.7.14), 실행 파일이 use 하기 전에는 그 어떤 항목도 범위에 없습니다. 어느 target 에서든 pkg:: 는 그 target 자신의 루트입니다. target 마다 자기 모듈 트리가 있으므로 둘 다 같은 src/util.rok 에 대해 mod util; 을 선언할 수 있으며, 각자 자기 사본을 얻습니다. 이 패키지에 의존하는 패키지는 라이브러리만 얻습니다.

      #0.3.2. 파일과 모듈

      패키지 안의 추가 모듈은 src/ 아래의 파일로서 두 형태 중 하나를 택합니다.

      foo.rok                <- single-file module (no submodules)

      또는 다음과 같이 폴더를 동반하는 형태로 둘 수도 있습니다.

      foo.rok                <- module body
foo/                   <- foo's submodules
├── bar.rok                foo::bar submodule
└── baz.rok                foo::baz submodule

      폴더 형태에서는 본체 파일 (foo.rok) 과 같은 이름의 폴더 (foo/) 가 함께 놓입니다. 이때 본체 안에 mod 이름; 으로 선언된 서브모듈만 폴더 안의 파일과 매핑됩니다. Rust 2018+ 와 같은 규칙이며, 자세한 매핑 규칙은 모듈 에서 정의합니다.

      한편 별도 파일 없이 본체 안에 mod 이름 { ... } 또는 pub mod 이름 { ... } 형태로 인라인 모듈을 둘 수도 있습니다. Rust 의 인라인 모듈과 같은 동작이며, 자세한 형태와 매핑 역시 모듈 에서 정의합니다.

      #0.3.3. 패키지 식별자

      각 패키지에는 내용 기반 해시가 부여됩니다. 해시 입력은 패키지의 모든 소스 파일을 src/ 기준 상대 경로 (/ 구분자) 의 바이트 순서로 정렬해 이어 붙인 것이며, 각 파일은 경로 + \0 + 내용 + \0 으로 직렬화합니다. 그 SHA-256 의 앞 8 글자를 식별자로 사용합니다.

      이 해시는 다음과 같은 성질을 가집니다. 같은 내용의 패키지는 어디서 빌드해도 같은 해시가 나오며, 한 글자라도 바뀌면 새 해시가 만들어집니다.

      이 해시는 산출물의 심볼 이름과 캐시 키에 사용되며, 구체적 사용처는 후속 문서에서 정의합니다.

      #0.3.4. 매니페스트 (rok.rokon) 는 선택

      패키지의 정의는 파일 존재만으로 결정됩니다. 디렉토리에 src/main.rok 나 src/lib.rok 가 있으면 그 디렉토리가 패키지이고, 어느 것들이 있느냐가 실행 파일, 라이브러리, 또는 둘 다를 가지는지를 정합니다. 매니페스트는 이 규약을 바꾸지 않습니다.

      의존성, dev 의존성, toolchain 고정 같은 정보가 필요할 때만 패키지 루트의 src/ 옆에 매니페스트 rok.rokon (9.10.3) 을 두고, 도구가 해소한 결과는 lockfile rok.lock 에 남습니다. 두 파일 이름은 이 철자 그대로 (모두 소문자) 입니다. 대소문자가 다른 이름 (Rok.rokon 등) 은 경고입니다. 두 파일은 ROKON 형식이며, 매니페스트는 Package { .. } 값 하나로 읽기만 하고 컴파일하거나 실행하지 않습니다.

      이 결정은 두 가지를 가능하게 합니다. 첫째로 의존성이 없는 패키지는 컴파일러가 파일만 보고 처리할 수 있습니다. 둘째로 매니페스트는 추가될 뿐이며, 기존 패키지 정의를 깨지 않습니다.

      #0.3.5. 테스트와 벤치마크 디렉토리

      패키지는 src/ 옆에 tests/ 와 benches/ 디렉토리를 둘 수 있습니다. src/ 밖의 다른 파일 (0.3.1) 과 달리 이들은 컴파일되지만, 대응하는 명령에서만 그렇습니다: tests/ 는 rokc test, benches/ 는 rokc bench. 일반 빌드, 라이브러리 인터페이스 (.rokhir), 패키지 식별자 (0.3.3) 에는 들어가지 않으며, 이들은 모두 src/ 만으로 정해집니다.

      각 디렉토리는 합성 루트 모듈로 올라갑니다 - tests/ 는 tests 모듈, benches/ 는 benches 모듈 아래에 - 모듈 의 일반 레이아웃 규칙을 따릅니다: tests/parse.rok 는 tests::parse 이고, 옆의 tests/parse/ 폴더가 그 모듈의 하위 모듈을 담습니다. mod.rok 는 없습니다 (5.4.6); 이름 규칙은 src/ 와 같습니다.

      코드는 in-crate 입니다: 패키지와 함께 컴파일되며 pkg:: 로 패키지에 닿고, src/ 아래 모듈과 동일한 패키지 내부 가시성을 가집니다 - 의존성의 pub 전용 뷰가 아니므로 pub(pkg) 항목과 패키지 자신의 비공개 모듈까지 다룰 수 있습니다. 매니페스트의 dev_deps (9.10.3) 를 쓸 수 있습니다. src/lib.rok 와 src/main.rok 를 둘 다 가진 패키지에서는 두 디렉토리가 라이브러리를 대상으로 빌드되며, 실행 파일 자신의 테스트는 src/ 안에 인라인으로 둡니다.

      여기의 파일은 암묵적으로 test/bench 전용이라 #[cfg(test)] 가 필요 없습니다. 측정 함수는 #[test] 나 #[bench] 로 표시하고 (6.2.5), 디렉토리의 다른 항목은 공용 헬퍼입니다.

      my_lib/
├── rok.rokon
├── src/
│   └── lib.rok
├── tests/                <- rokc test 전용
│   ├── parse.rok             tests::parse   (pkg:: 사용)
│   └── common.rok            tests::common  (공용 헬퍼, #[test] 없음)
└── benches/              <- rokc bench 전용
    └── parse.rok             benches::parse
