      #rok 표준 라이브러리 참조

      이 사양은 rok 표준 라이브러리의 형식 사양 (formal specification) 입니다. 언어 자체의 사양이 문법과 의미 메커니즘을 정의한다면, 표준 라이브러리 사양은 그 메커니즘이 실제로 작동하기 위해 필요한 타입과 트레잇, 함수의 의미를 채웁니다. 연산자가 어떤 트레잇으로 풀리는지, 컬렉션이 어떤 인터페이스를 갖는지, 비동기와 I/O 가 어떤 약속 위에서 동작하는지를 한 자리에서 정의합니다.

      언어 사양은 refs-lang/ 에 별도로 모여 있으며, 본 문서는 사양만을 다룹니다. 라이브러리의 실제 구현은 spec 의 범위 밖에 있습니다.

      중요

      언어 사양 ↔ 표준 라이브러리 사양의 경계

      refs-lang 은 문법과 의미 메커니즘 을 정의합니다 (예: + 토큰이 어떤 트레잇 메서드에 매핑되는지). refs-standard-libraries (이 문서) 는 그 트레잇 자체의 시그니처와 의미 를 정의합니다 (예: Add::add 가 어떤 숫자 변환을 적용하는지).

      두 사양 모두 같은 표기법 규약 을 따릅니다.

      #3-tier 모델

      표준 라이브러리는 단일한 평면이 아니라 세 개의 층으로 나뉘어 있습니다. 시스템 프로그래밍의 거의 모든 코드는 안전한 추상 위에서 작성되지만, 그 추상을 구현하려면 결국 어디선가 원시 메모리와 FFI 를 다루어야 합니다. 또한 파일이나 네트워크처럼 호스트 환경이 있어야만 의미를 갖는 기능은, 임베디드처럼 그러한 환경이 없는 target 에서는 아예 존재하지 않아야 합니다. 이러한 차이를 의존성 그래프로 그대로 드러내기 위해 가상 네임스페이스 rok:: 아래 rok::bare / rok::core / rok::std 의 3-tier 구조를 따릅니다.

      rok::bare   (base, runtime extern "C" 만 의존)
  ↓
rok::core   (foundation, 안전, 모든 target - uses rok::bare internally)
  ↓
rok::std   (target-dep - uses rok::core + rok::bare)

      즉 rok::bare 는 가장 아래에서 원시 능력만을 노출하고, rok::core 는 그 위에서 안전한 foundation 을 모든 target 에 동일하게 제공합니다. 한편 rok::std 는 rok::core 위에 호스트 의존 기능을 얹어 일반적인 응용 프로그램이 기대하는 표면을 완성합니다. 일상적인 코드는 rok::core 만으로 충분하고, OS 자원이 필요해지는 순간 rok::std 로 손을 뻗으며, 추상의 경계를 직접 넘어야 할 때만 rok::bare 를 명시적으로 import 합니다. 자세한 의존성 규칙은 0.1 tier 모델 에서 다룹니다.

      Tier경로디렉토리영역
      rok::barerok::bare::*100-bare/Ptr, ConstPtr, transmute, raw alloc, pin
      rok::corerok::core::*200-core/숫자, 연산자, iter, 컬렉션, fmt, sync, task
      rok::stdrok::std::*300-std/fs, net, time, thread, io, env, process, path, crypto (random)

      #장 목차

      #0. 메타 - 000-meta/

      라이브러리 전체에 걸친 정책과 표.

      • 0.1. 3-tier 모델
      • 0.2. import 정책 (use rok::core::**; 묵시 적용)
      • 0.3. intrinsic 메커니즘 - 컴파일러 ↔ 표준 라이브러리 경계
      • 0.4. #[lang] 슬롯 매핑 표
      • 0.5. 표기법

      #1. Unsafe - 100-bare/

      저수준 / 위험 영역. 명시 import 필수.

      • 1.1. Pointer 계열 (Ptr/ConstPtr/ManyPtr/CPtr - Zig arity-encoded + Rust strict provenance)
      • 1.2. cast 연산 (ptr_cast/align_cast/const_cast/reinterpret)
      • 1.3. MaybeUninit<T> + Pod + raw mem ops
      • 1.4. raw allocation
      • 1.5. volatile 메모리 접근
      • 1.6. Pinned<T> - GC pin (Go 1.21 Pinner 모델)
      • 1.7. FFI - extern "C" / CStr / CString
      • 1.8. WASM Component Model (ffi.wit)
      • 1.9. rok::bare::mlir - MLIR 다이얼렉트 직접 접근
      • 1.10. rok::bare::mlir::plugin - 사용자 정의 다이얼렉트 등록

      #2. Rok - 200-core/

      안전 영역. 모든 target. use rok::core::**; 묵시 적용 (별도 prelude 모듈 없음).

      • 2.1. 숫자 타입 (int, float, auto-promote)
      • 2.2. niche wrapper (NonZero, NonNan, Finite, Positive)
      • 2.3. 산술 / 비트 트레잇 (Add, Sub, ..., Shl, Shr)
      • 2.4. 복합 대입 트레잇 (AddAssign, ...)
      • 2.5. 비교 트레잇 (PartialEq, Eq, Ord, PartialOrd, Hash)
      • 2.6. broadcast 트레잇 (DotAdd, DotMul, ...)
      • 2.7. iter 트레잇 (Iterator, IntoIterator)
      • 2.8. Stream (async iterator)
      • 2.9. 컬렉션 (List, Dict, Set, Tuple, Slice)
      • 2.10. fmt (Display, Debug, Formatter)
      • 2.11. 변환 (From, Into, TryFrom, saturating_into, ...)
      • 2.12. 리플렉션 (Reflect, Inspect)
      • 2.13. marker 트레잇 (Clone, Copy)
      • 2.14. 에러 타입 (TypeError, ValueError, ...)
      • 2.15. 문자열 (str 가변 단일, char, c_char)
      • 2.16. sync primitive (Atomic, Mutex, RwLock, Cell)
      • 2.17. Channel
      • 2.18. task:: API
      • 2.19. par:: API
      • 2.20. Future / await 통합
      • 2.21. crypto:: - 해시, MAC, AEAD, 키 교환, 서명

      참고

      텐서 / 자동 미분 / SIMD / GPU 등 과학 컴퓨팅 / AI 영역은 표준 라이브러리에 포함되지 않고 외부 라이브러리로 분리됩니다. 외부 라이브러리는 rok::bare::mlir 모듈을 통해 MLIR 다이얼렉트에 직접 접근할 수 있습니다.

      #3. Std - 300-std/

      target-dep 영역. 명시 import.

      • 3.1. fs:: - 파일 시스템 (atomic ops, Dir capability, reflink)
      • 3.2. net:: - TCP/UDP/Unix + TLS 1.3 (HTTP 외부)
      • 3.3. time:: - Instant / SystemTime / Duration / BootTime
      • 3.4. thread:: - OS 스레드 (1:1, task 와 별개)
      • 3.5. io:: - Reader / Writer / stdin/out/err (sync 만 - async 트레잇 없음)
      • 3.6. env:: - 환경 변수 / args / 디렉토리
      • 3.7. process:: - Command / pidfd / kill_on_drop
      • 3.8. path:: - UTF-8 Path + / 연산자 (Python pathlib 식)
      • 3.9. rokon:: - ROKON 데이터 형식 (.rokon)
      • 3.10. crypto:: - OS 난수 원천

      #읽는 방법

      #처음 읽을 때

      처음 접근한다면 먼저 refs-lang 의 0~6 장을 따라 언어의 메커니즘을 이해한 다음, 그 위에 본 문서를 얹어 읽기를 권합니다. 본 문서는 refs-lang 이 정의한 메커니즘에 의미를 부여하는 역할을 하므로, 메커니즘에 대한 감각이 없으면 트레잇과 시그니처가 공중에 뜬 채로 읽히기 쉽습니다. 따라서 두 문서를 함께 두고 오가며 읽는 편이 가장 효율적입니다.

      #참조용

      각 항목은 안정 섹션 번호 (<chapter>.<section>) 로 식별합니다. 이 번호는 내부 링크와 외부 참조 모두에서 동일하게 사용되므로, 파일이 옮겨지더라도 안정적으로 가리킬 수 있습니다.

      refs-standard-libraries 2.3        →  rok ops (Add/Sub/...)
refs-standard-libraries 1.1        →  unsafe Ptr<T>
refs-standard-libraries 3.5.2      →  std io (특정 하위 섹션)

      #검색

      특정 트레잇이나 함수를 빠르게 찾고 싶다면 ripgrep 으로 디렉토리를 좁혀 검색하는 편이 가장 가볍습니다.

      rg "trait Add" spec/ko/refs-standard-libraries/200-core/
rg "fn into" spec/ko/refs-standard-libraries/

      #디렉토리 / 파일 명명

      본 문서는 refs-lang 과는 다른 디렉토리 컨벤션을 따릅니다. 두 사양이 서로 다른 모양을 갖기 때문인데, refs-lang 은 0 부터 9 까지의 장이 모두 같은 권위를 갖는 평면 구조인 반면, refs-standard-libraries 는 3 개의 tier 가 cross-reference 의 핵심 정보로 작동하는 계층 구조입니다. 이러한 구조 차이를 디렉토리 이름의 자릿수로 그대로 드러냅니다.

      사양prefix이유
      refs-lang한 자리 (002-)10 장 (0~9) 이 모두 같은 권위 - flat 모양
      refs-standard-libraries세 자리 (200-)3 tier × N 모듈 - tier 가 cross-reference 의 핵심 정보

      구체적인 파일 이름 규칙은 다음과 같습니다. tier 디렉토리는 100 단위의 prefix 를 갖고, 그 안의 모듈 파일은 tier 한 자리와 모듈 두 자리를 합친 세 자리 prefix 로 시작합니다.

      위치형태예
      Tier<TNN>-<descriptive-name>/100-bare/, 200-core/
      모듈<tier><module>-<name>.md203-ops.md, 211-conversion.md
      (tier 한 자리 + module 두 자리)
      README각 tier / 장에 README.mdTOC + 개요

      이처럼 파일 경로 자체에 tier 정보가 인코딩되어 있지만, 외부에서 본 문서를 인용할 때는 어디까지나 안정 섹션 번호 (2.3.1 등) 가 정식 표기입니다. 파일 경로는 IDE 와 GitHub 에서의 탐색 편의를 위한 보조 표기로만 쓰입니다.
